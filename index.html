The problem

The school has a small, non-technical administration team and a single modest office PC. Its records and processes need to move from manual and spreadsheet-based work into a system that is straightforward to operate and maintain.

My approach

I documented business rules in a client agreement before implementation, then organised development into small, independently specified features. Financial workflows receive particular attention because fee and receipt errors directly affect school records.

High-level architecture

Each feature follows a repeatable sequence. The client agreement establishes the business rules; the specification defines expected behaviour; implementation and independent verification follow.

  1. 1. Client agreementDocument scope, terminology and business rules.
  2. 2. Feature specificationDefine acceptance scenarios and clarify open questions.
  3. 3. Plan and tasksDescribe data, API and UI changes; split work into manageable tasks.
  4. 4. Test planningA separate subagent derives test scenarios from the specification.
  5. 5. ImplementationImplement feature tasks using project rules and hooks.
  6. 6. Test writingA separate role creates tests for the implemented behaviour.
  7. 7. Test executionA runner executes the suite and reports failures.
  8. 8. ReviewA reviewer checks the changes against the spec and project rules.
  9. 9. ReleaseAfter verification, push the branch and create the release tag.

Feedback loop: failed checks return to implementation for correction and are rerun before the feature is considered complete.

Why split the agent roles?

  • The test planner works from the specification rather than implementation details, helping reduce shared assumptions.
  • Separate test-writing, execution and review responsibilities provide distinct verification steps.
  • A task limit of 30 keeps feature work easier to inspect and manage.

Fee and receipt behaviour was defined before coding, including the less common cases that can otherwise create inconsistent financial records.

Revising a fee structure

  1. Admin enters fee amounts by standard and category.
  2. Admin finalises the academic year.
  3. A revision warns that student fees for that year will be recalculated.
  4. Admin confirms the revision.
  5. Fees are recalculated; existing receipts remain unchanged.

Handling a cheque

  1. Admin enters receipt number and date and confirms before saving.
  2. Cheque is counted as paid when received.
  3. If it bounces, it is marked as not cleared.
  4. The amount is added back to the outstanding balance.
  5. The reversal is recorded in the audit log.

Other agreed rules

  • Payments can be made in any amount at any time. The “fees paid up to” date is derived from total paid and the daily fee from the academic-year start.
  • Receipts cannot be edited or cancelled, and overpayment is rejected.
  • The current academic year is determined from today's date; an applicable year must exist.
  • Standard and category cannot change within a finalised year, while division can.
  • Late fees, caution money and mid-year admission are explicitly out of scope.

OmniCode Working prototype

    The problem

    Teams may not be able to send proprietary source code to public AI models. At the same time, a smaller on-premises model may not be as effective at planning a multi-step investigation. The challenge is to combine cloud reasoning with controlled access to local code.

    The approach

    Separate reasoning from source-code access. The cloud model works with pseudonymised metadata and tool results. A local model can inspect real code for narrow questions, while its response is masked before it is returned to the cloud reasoning flow.

    3Core layers: MCP server, agent host, UI and gateway
    8Typed tools exposed to the agent
    LocalSource-code analysis stays on-premises by design
    PrototypeAccuracy and privacy require further validation

    Current status: Working prototype. Answer accuracy has not yet been benchmarked, and the privacy design should not be interpreted as a formally verified zero-leakage guarantee.

    The user question is pseudonymised before it enters the cloud reasoning flow. The MCP layer owns repository access and invokes local analysis when needed. De-masking happens only on-premises: inside the MCP layer, to resolve names for local lookups, and in the user's interface for display.

    The prototype uses multiple controls to reduce the chance of proprietary code or identifying names entering the cloud reasoning context.

    1. Prompt masking. User input is masked and scanned against the repository index. A detected unmasked repository identifier can block the run.
    2. Restricted agent tools. Built-in file, shell and web capabilities are denied; the agent is intended to use only the exposed OmniCode tools.
    3. Eight typed tools. Tools cover code search, call graph, file listing, log analysis, database schema, workflow steps, documentation search and on-premises questions.
    4. Masked tool results. Results are masked and scanned before they are passed back into the cloud reasoning context. Unresolved content can be withheld.
    5. Local code questions. Questions requiring source-level understanding are delegated to the on-premises model, with its response masked before returning.
    6. Display-time de-masking. Real names are restored for display in the authorised interface after the cloud model has completed its work.
    7. Audit trail. Tool calls, blocks and de-masking events are logged to support inspection of the workflow.

    Designed to stay local

    • Source code bodies
    • Mapping between real names and pseudonyms
    • Raw logs and uploads
    • Raw prompts and answers used for local model analysis

    Intended cloud context

    • Masked user questions
    • Masked tool results such as signatures, call graphs and schema metadata
    • Reasoning and generated answers expressed using pseudonyms

    One question travels through three layers. Names are masked on the way out, the cloud model only ever sees pseudonyms, and each hop has its own guardrail. Pink dots mark steps that write to the audit trail.

    UI and gatewayClaude hostMCP serverGuardrailAudited step

    How the vault is created

    1. Session first. A random sessionId is created and saved against the logged-in user. Only that user can stream or replay the run.
    2. Vault second. An empty table maps real names to tokens for that one session. The same name always gets the same token inside a session.
    3. Names are found, not guessed. Every word in the prompt, logs, traces and files is checked against the repository's own symbol index of classes, methods, tables and packages. Ordinary words such as "service" are not treated as secrets.
    4. The agent never handles the id. The runner attaches the sessionId to every tool call, so Claude cannot choose or guess another session.

    Audit trail and graphs

    Design note: security events record the reason for a block, never the payload, so the audit trail does not become a second place where sensitive content is stored.

    Take the question “explain comment sync in the SDK”. The search runs against an index of the repository that was built earlier with Tree-sitter: code nodes, call edges and a full-text table. Nothing is searched by reading raw files at question time.

    What happens, step by step

    1. Clean the question. Lowercase it and keep words longer than two letters: comment, sync, sdk.
    2. Keyword search. A full-text index returns the best-matching symbols. The top hits become seeds for the next step.
    3. Call graph. Each seed passes part of its score to its callers and callees. Neighbours whose names share no word with the question keep only a quarter of the boost.
    4. Meaning search. A small local embedding model compares the question with each symbol's name, signature and docstring.
    5. Merge with RRF. The three ranked lists become one ranking; the top ten move on.
    6. Mask and return. Real code outlines are read on-premises, names are replaced by tokens, the scanner checks the result, and a size-capped page goes back to the cloud model.

    What RRF means

    Reciprocal Rank Fusion merges ranked lists using only each item's position, not its raw score. Every list gives 1 ÷ (60 + rank) and the scores are added. Something several searches like beats something only one likes.

    Why weights differ

    Keywords count most (1.6) because they follow what the user typed. Meaning counts 1.0 and the call graph 0.7, as supporting evidence. If one search returns nothing, the others still work.

    Honest limit: retrieval quality has not yet been measured against labelled questions. The current benchmark only checks for leaks, speed and a rough keyword hit rate.

    The same code ships three ways: as an installable Python library, as a Claude Code plugin, and as a container stack. A workspace file keeps it generic, so repository paths, masking patterns, the local model and the storage backend are configuration, not code.

    Python library

    • Packaged with setuptools; commands for the MCP server, the gateway and database migrations.
    • Public API: workspace config, an agent that runs one masked turn, hooks, custom tools, storage.
    • Installed editable during development; a private wheel is the route for sharing. It is not published publicly.

    Claude Code plugin

    • A folder with a manifest, the MCP server entry, two hooks, JSON specs and a reasoning contract.
    • The specs hold the tool allowlist, the denied built-in tools and the on-prem limits.
    • A small script zips it into a distributable package.

    Deployment

    • Windows setup script: creates a virtual environment, installs the library, runs the health checks, then the 28 attacks, and stops if any fail.
    • Docker Compose: a Python image with a JDK and the Claude Code CLI, running as a non-root user, plus PostgreSQL. Index and vault live in a volume; the analysed repository is mounted from the host.
    • On-prem model: reached over a local address; the health check confirms it is on loopback or an allowed host.
    • Kill switches: one environment variable stops all tool execution; another disables only the on-prem tool.
